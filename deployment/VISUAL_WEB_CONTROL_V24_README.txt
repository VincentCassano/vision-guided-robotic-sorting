v24-fix2 网页真机控制：持续存在满2秒才计入检测统计

使用方法
1. 在机器人上退出正在运行的旧抓取程序和旧相机程序，避免并行占用。
2. 将本包放~/test，按 VISUAL_WEB_CONTROL_V24_ONSITE_COMMAND.txt 校验、解压并启动。
3. 自动打开 http://127.0.0.1:18081 。默认尝试1440×940普通浏览器窗口，不请求全屏。
   有Chromium/Chrome时显式设置窗口尺寸；其他浏览器沿用其窗口偏好，可直接拖大。
4. 启动只开相机、识别和网页。点击“自动分拣”执行原a批次；“单件取放”执行原m。
   三色同规格直立断电圆柱，已有头/板/绑定/工作区不变；原整手及含物扫掠清空并现场守急停的条件保持。
5. “停止”独立锁存停止请求，并写原批次stop/当前worker abort文件，不靠stdin排q；不自动重发动作。
   “重置”只重置软件任务，不松手、不回臂、不清控制器错误。真实故障仍由成功版原规则处理。
6. 关闭浏览器不会停止控制服务。终端Ctrl+C会请求停止，等待原动作进程收尾，再关闭相机和推理。
   软件停止不等于硬件急停或已证实物理停稳；意外运动/碰撞使用现场硬件急停。

界面与实际数据
- 参考用户提供的SortAI深蓝控制台：实时画面、控制区、检测/动作统计、真实系统日志。
- 相机由唯一后台服务持续占用。观察、下降、夹持、提起、转运、投放和空手返回期间均保持实时预览。
- 黄色框PENDING为尚未满2秒的候选；绿色CONFIRMED为连续存在满2秒的目标；蓝框为本轮已锁定抓取目标的采集位置。
- 网页MJPEG只展示。定位消费者取得原1280×720无损BGR图及同一帧的YOLO结果；核对帧号、图像SHA与内参。
- 每次采集从服务当前时刻之后的新鲜帧开始；保留原8帧/2秒及原几何/稳定性规则，不读旧画面代替现场。
- 运动期间坐标保持原成功版锁定策略，不因实时画面中出现手或被抓物而追改当前轨迹。
- 检测数量只计当前仍可见、同类别与位置跨帧对应且连续存在至少2秒的目标；不是所有原始检测框，也不是每帧累加。
- 只在新的真实推理帧到达时，用其采集时刻推进连续计时；单帧等待2秒、重复网页轮询均不能确认目标。
- 漏检、类别改变、关联不明确或两次处理帧间隔超过2秒，重新开始确认；相机/推理故障或结果过期时显示等待。
- 本修复仅影响显示统计，原始detections、同帧图像、视觉定位与动作指令均保持。
- 已完成数是本批动作周期数；实际抓稳、滑落和正确入框尚未自动验证，不显示虚构成功率。

局域网使用
启动参数增加 --host 0.0.0.0；其他电脑访问 http://运行程序的Ubuntu局域网IP:18081 。
用 hostname -I 查看Ubuntu地址。当前发布的启动命令已带此参数。

HTTP接口（默认仅机器人本机；局域网由上述参数开启）
GET /api/status：真实任务阶段、动作周期、目标、相机状态及日志。
GET /live.mjpg：持续实时预览。
POST /api/command，Content-Type: application/json，内容仅 {"command":"START_AUTO"}。
可用 START_AUTO、START_SINGLE、START、STOP、RESET、MODE_AUTO、MODE_MANUAL。
GET请求不启动动作；按钮重复点击不会排入重复抓取任务；网络未确认不会自动重发。

可选ROS接入（网页版运行不需要ROS Master）
在已配置ROS环境的另一个终端：
source ~/catkin_ws/devel/setup.bash
cd ~/test/battery-d435-preview
/usr/bin/python3 deployment/task_control_ros_v24.py
服务沿用 /battery_grasp/start、stop、reset、mode_auto、mode_manual、status；
话题 /battery_grasp/state、/sorting_state、/sorting_result、/selected_battery_target。
这些服务转发到同一个真机HTTP控制器，不构造SimExecutor，不创建第二个SDK动作执行器。
同名仿真服务存在时拒绝覆盖；先退出仿真控制。ROS桥未完成现场联调，非网页启动依赖。
